# 尘缘问道｜实施计划与任务拆分 v0.3

日期：2026-10-13。状态：计划草案，尚未执行工程开发。以 01_设计规格.md 为产品范围基线，成长数值详见 05_成长与数值系统修订.md。

## 1. 实施原则

先证明物品产消与修炼、战斗、突破组成的可重复小循环，再扩大内容；美术组件与玩法并行，不能先制作全部大图，再发现界面不可用。每个阶段都交付能运行和检查的版本，不以“页面画完”或“代码写了多少”作为完成标准。

建议技术栈为 Vue 3 + TypeScript + Vite + Pinia，游戏规则采用独立 TypeScript 模块，存档使用 IndexedDB，测试采用单元测试与 Playwright 浏览器测试。实际依赖版本在开工时选稳定兼容版本并锁定，不把本文当作包版本清单。

Vue 官方指南推荐 Pinia 用于新应用的共享状态管理 [S2]。本方案的 Pinia 主要承接已结算的状态与视图，不允许每个组件自行修改资源。

网页主要元素用 DOM/CSS，装饰用 SVG/图片，少量 Canvas 氛围可选。不使用完整 3D、地图寻路引擎或在线大模型。按静态站点构建部署；Vite 官方部署文档说明默认构建输出为 dist，而 vite preview 只用于本地预览，不是正式生产服务器 [S3]。

## 2. 团队与排期假设

参考配置：开发 A 负责界面、存档与发布；开发 B 负责规则、数值工具与测试；美术/界面设计 1 人；策划/文案 1 人，兼组织测试。测试修复时间计入排期，不假定全部工时都用于写功能。

在上述人数、有限资产、无服务端与授权等待的前提下，先按六周窗口规划。它是范围估算，不是工期承诺；完成初始经济模型与首境界闭环后重新评估。本轮把物品与数值验证提前，原六周仅为可重排窗口，不因沿用表格就表示新增工作无需工时。少于该人员配置时，应缩减内容或放宽周期，而不是删除验证、存档和恢复工作。

美术或音乐采购金额未确定，不在缺少报价的情况下编造项目总成本。

## 5. 第一批真正要交付的东西

1. 可从浏览器打开的主界面，而不是整图加热区。
2. 一套由规则维护的角色状态，以及能保存/恢复的事件。
3. 破庙三选一，三个选择都有真实成本或收益；所有分支可入道。
4. 剑、符各一套小组合，对同一个敌人呈现不同决策。
5. 材料获取、炼制、购买、修炼加速共享真实预算；通过自己的资源安排取得筑基条件，不由开场任务直接升境界。
6. 修为足够而物资不足时能看到缺口与来源；合成、突破及存读档均正确扣除和恢复。
7. 演示完整首境界资源循环，不对玩家完成所需分钟数作硬性要求。

不同时启动全部支线、多个地图大图、复杂动效、后台管理界面。M1 发现战斗无差异时先调规则，发现事件无吸引力时先调取舍，而不是添加第三流派。

## 6. 工程结构建议

```text
src/
  app/                 启动、页面组织
  ui/
    components/        纸面板、按钮、进度条、选项、头像等
    views/             修行、历练、行囊、仙缘
    overlays/          战斗、突破、结局、存档与设置
  game/
    types/             状态、指令、结果与内容类型
    engine/            校验、结算、效应、条件、随机数
    systems/           修炼、战斗、物品、经济、因果、章节
  content/             realm/skill/item/source/recipe/price/npc/event/encounter 数据
  persistence/         IndexedDB、迁移、检查点、导入导出
  telemetry/           本地试玩事件记录与导出
  assets/              可替换美术与音频资源
scripts/
  validate-content/    唯一 ID、引用、范围、必需分支校验
  replay-routes/       固定 seed 与指令序列路线回放
 tests/                单元、流程、浏览器测试
```

不创建通用可视化编辑器；本版用受类型/规则校验的 JSON 或 TypeScript 数据。现有效果能表达的新事件或技能主要填配置；新的机制仍需编写 resolver 和测试。

## 7. 发布与演示

生产包构建为静态资源，由正式静态托管服务/服务器提供。不得把 vite preview 当成线上生产服务器 [S3]。不通过双击 file:// 作为默认交付方式；本地演示需附启动静态服务的说明。

首次发布至少含：版本标识、可玩构建、源码和内容、运行说明、素材来源登记、存档格式说明、检查结果、演示操作脚本。

八分钟演示脚本建议：1 分钟从新游戏展示画面与选择；2 分钟展示两流派短战斗；2 分钟从合法节点展示因果回响；2 分钟展示渡劫；1 分钟展示结局与生平。演示跳转仅从主菜单的“演示节点”进入，标记“演示存档”，使用同一规则，不改正常存档。

演示档按当前内容版本由指令回放生成，不手填不可能的装备/境界组合。普通新玩家入口必须能从头通关。正常游玩不依赖开发控制台或现场修改数据。

## 8. 开发过程控制

每次提交检查：类型/格式、内容引用、单元测试、关键回放、生产构建。主分支保持可运行，较大功能以小步合并，避免最后一周才集成。

只收集本地试玩必要事件：新局、选项、战斗结果、境界、存档错误、结局和重玩。每条记录 runId、内容/经济版本、seed、事件 ID、会话 ID、相对会话时间，以及来源/消耗、行动数、突破缺口等必要字段；默认不上传道号、设备指纹或个人信息。测试者主动导出记录。约 30 分钟观察理解，不在玩家关闭网页时记作失败。区分继续原档、新开存档与达成飞升；会话计时仅作分析，不输入经济规则。

Playwright 官方提供截图比较能力 [S6]；本项目应在相同测试环境中冻结动效、固定字体加载和固定存档再生成基准图，以避免环境差异误报。初期以布局与可操作性为主，截图相似不替代功能测试。

## 9. 扩展性验收，不靠“预留入口”

在规则已有的前提下，增加一个事件、一种有完整材料来源的固定配方和一件使用既有效果的法宝：不改主界面组件，不改存档结构，可正常展示、结算和保存。再证明新增一种效应只影响对应规则与测试，而不是修改所有页面。

不为了未来多人化提前搭账号、服务器、支付和复杂插件机制。将来引入多人经济时另评估服务端权威状态与安全边界，不能把云存档等同于多人能力。
