# 尘缘问道｜数据与状态契约 v0.3

状态：面向实现的数据规格与样例，不是已实现的运行时或完整游戏源码。

## 1. 三个边界

内容配置回答“有什么”：功法、物品、章节、事件、敌人意图。游戏状态回答“这一局现在怎样”：当前境界、资源、已选因果、未决事件；引导完成状态不控制突破。规则引擎回答“这次行动是否合法，产生什么结果”。

UI 只提交有类型的指令并显示结果，不能直接扣背包、加修为或推进任务。文本描述不得成为奖励真源；奖励面板和叙事中的数值由已结算的结构化结果填入。

## 2. 状态最小字段

```typescript
// 接口示意：具体字段类型须在 E02 中实现并校验。
interface GameState {
  schemaVersion: number;
  contentVersion: string;
  balanceVersion: string;
  runId: string;
  revision: number;
  rngState: { algorithmVersion: number; state: number[] };
  mode: 'idle' | 'event' | 'battle' | 'breakthrough' | 'ending';
  world: { locationId: string; elapsedMonths: number; chapterId: string };
  player: {
    name: string;
    originId: string;
    realmId: string;
    xp: number;
    hp: number;
    mp: number;
    ageAtStartMonths: number;
    lifespanMonths: number;
    spiritStones: number;
  };
  inventory: Record<string, number>;
  onboarding: { completedStepIds: string[] };
  economy: {
    claimedOnceSourceIds: string[];
    guaranteedSourceProgress: Record<string, number>;
  };
  learnedSkillIds: string[];
  equipped: { mindId: string | null; artIds: string[]; artifactId: string | null };
  flags: Record<string, boolean | string | number>;
  npcStates: Record<string, string>;
  questStates: Record<string, string>;
  completedEventIds: string[];
  activeEvent: EventInstance | null;
  battle: BattleSnapshot | null;
  latestResult: ActionResult | null;
  keyHistory: HistoryEntry[];
}
```

EventInstance 必须含 instanceId、eventDefinitionId、已确定的选择上下文与抽取结果。BattleSnapshot 必须含敌我当前状态、回合号、已公开意图、状态持续时长和所有继续结算所需字段。上述类型是待定义接口，不应把此代码片段当作可直接编译的完整文件。

基础属性可由境界、功法、法宝与永久奖励派生；不要同时在多个地方保存相互矛盾的攻击力副本。hp/mp 是当前量，最大值由规则得出并校验。时间统一按整数月处理，避免年龄与世界时间重复累加。

## 3. 指令与原子提交

每条指令至少包含 commandId、runId、expectedRevision、type、payload。commandId 在一次用户意图的重试中保持相同，不因网络/保存重试重新生成。

提交顺序：

1. 在当前内存快照上验证规则状态、资源、前置条件与装备限制。
2. 纯规则计算 nextState、结构化结果与演出提示，不写入半成品。
3. 在一次 IndexedDB 读写事务中读取该 run 的最新 revision 和已处理 commandId；若过期则拒绝并重载，若已处理则返回此前结果。
4. 同事务写入完整下一快照、commandId 结果记录和必要检查点。
5. 只有事务完成后才将结果发布到界面并播放演出。

同一事务原子保存可以借助 IndexedDB 的事务能力 [S4]；这仍需要正确实现完成/失败监听与异常处理，不是调用一次 put 就等于已验证可靠。

事务失败时保留行动前状态并显示“未保存”，允许原指令重试或导出已有快照。不悄悄进入内存游玩并显示已保存。确需提供临时会话模式时必须显式告知不保证恢复，首版可不实现。

不能只靠按钮置灰防止重复奖励。规则状态、revision 和 commandId 检查三者共同约束。另一标签页提交了新状态时，本标签页提示重载，不覆盖其进度。

## 4. 内容契约

基础实体有稳定 id、名称、展示说明、开启条件和效果列表。效果仅实现本 Demo 需要的范围，如：修为变化、物品增减、解锁技能、设置标记、变更关系、推进叙事章节、推进时间、开始战斗、更新地点等。境界变更必须由专用突破指令检查完整条件，普通事件不直接设置境界。

现有条件操作符建议只支持 all/any/not 组合，以及境界比较、标记比较、物品数量、章节/地点、事件是否完成等必要原语。不使用任意字符串 eval；不能通过内容数据注入执行代码。

事件字段：id、locationId、chapterId、once、requires、text、choices。选项字段：id、label、preview、requires、costs、effects、resultText、nextEventId。

costs 表达必需且原子扣除的代价；effects 表达结果变化。禁止 costs 不足仍执行部分 effects。nextEventId 转入下一事件时须验证可解析，不能因选项路径拼错造成死路。

参考样例位于 examples/opening_event.json。它只演示第一事件契约；其中引用的物品、技能和下一事件仍需由对应内容文件实现，不能单独作为可玩游戏运行。

## 5. 条件剧情的约束

重要开场分支使用互斥单值，例如 flags.templeChoice = helped / traded / left；避免多个布尔标记同时为真。一个事件实例只允许结算一次。

叙事章节变化可以触发世界文本和事件更新，但不能自动推进境界、补齐修为或全量重抽事件池。通用随机奇遇使用可保存的随机状态；一旦展示就保存抽取结果。重复读取档案或刷新不能改变同一实例的内容。

主线事件有确定可达路径，支线条件不参与唯一主线锁。人物援助只改变终局难度和表现，不使未结缘的玩家必败。

## 6. 存档规格

建议保留 1 个自动档、1 个上一成功提交备份、当前大境界检查点和渡劫准备检查点。允许手动导出命名备份，首版不开发复杂云档。

保存内容含规则状态、随机状态、未决事件/战斗、已结算奖励记录和关键历史，不只保存角色属性。

导入处理：先限制体积并解析 JSON，校验 schemaVersion/contentVersion、ID 引用、整数与上下界、模式与 activeEvent/battle 一致性；全部通过再事务替换，失败不覆盖已有档。较新未知版本明确拒绝；旧版本仅经显式迁移函数转入，不静默清空。

浏览器存储可能因配额、隐私模式、用户清理或回收而失去数据；本地存档不是永久可靠的备份 [S5]。申请持久化即便使用也不得作为唯一保障。演示构建和线上构建用不同来源时，不能假定自动共享同一份存档。

## 7. 校验工具最低要求

配置构建检查：所有 ID 唯一；所有引用存在；不存在负成本、NaN、非法持续时间；法宝开启境界合法；事件分支都有结果或下一节点；任务身份标记不在商店出售；突破消耗物须有可达确定来源与成本。

运行时不变量：资源数量不为负；装备数量不超过上限；hp/mp 不超合法最大值；同一事件不重复领奖；未决事件、战斗与 mode 一致；修炼不会自动突破；突破不能略过修为与物资检查；教学计时不参与资源产出或境界判断。

最小路线回放：固定 seed、固定 command 序列和版本，验证两流派×三开场选择的六条新档到飞升路线。对故意不完成任务的无限行为不宣称“所有输入都可自动通关”；保证可达与恢复路径才是目标。

## 8. 边界与说明

本版为单机可信客户端，不宣称有防篡改或多人经济安全能力。存档校验防止意外损坏与不合法状态，不等于防作弊。

[S4] MDN IndexedDB API：`https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API`。
[S5] MDN 存储配额与回收：`https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria`。

## 9. 成长内容扩展契约

新增以下配置，不改变物品选择与战斗页面的通用结构：

| 配置 | 最低字段 | 校验重点 |
|---|---|---|
| Realm | id, xpCap, baseCultivationYield, lifespanMonths, breakthrough | 阈值与产出同版本；breakthrough 指向目标境界与消耗物 |
| Item | id, kind, uses, tradePolicy, minAcquireRealm | 数量合法；不因已知配方就忽略来源条件 |
| ResourceSource | id, repeatable, requires, costs, guaranteedRewards, optionalRewards | 一次性来源与重复行动分开；可选掉落不独占必需品 |
| Recipe | id, inputs, currencyCost, output, requires | 全部成本一次性检查；原子消耗与出品；无半次合成 |
| ShopOffer | itemId, buyPrice, sellPrice, requires | 检查完整交易/炼制循环，而非只查单品价差 |
| CultivationAction | id, yields, costs, requires, stopConditions | 收益、物资成本、游戏耗时一起预览；批量能被边界中断 |

获取来源查询必须调用同一套 requires 与成本配置，不在 UI 再手写另一套解锁条件。来源不可达时显示具体缺口，并不能形成“需要先突破才能取得突破材料”的环。

Breakthrough 指令在同一提交内完成：状态与上限检查 → 消耗物核对 → 扣除物资 → 切境界 → 修为按当前版本规则归零 → 能力与寿限更新 → 记史与检查点。配置必须明确是否另扣货币，不允许 UI 和配方各扣一次同一份炼制费。

批量指令按逐行动顺序执行，遇到事件、战斗、资源不足、修为满、目标已完成或寿元风险停止。随机状态与逐次行动保持等价；一次事务保存一个确定批次结果。不能用“单位收益×数量”跳过中间状态判断。大型批次上限须有限制，避免长事务；具体批次大小由工程验证。

新增 balanceVersion 时，旧档不直接套用新阈值导致负修为或物品失效。若尚未有已发布游戏存档，不虚构已存在的迁移能力；将来更改已发布经济版本须有明确迁移、兼容或拒绝导入策略。

约 30 分钟数据属于本地试玩记录，不是 GameState 的境界前置。onboarding 只记录用户已见提示或已完成行为，关闭教程不会改出货率、收益或突破成本。
