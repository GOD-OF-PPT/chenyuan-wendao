# 放置定位、界面清晰度与当前执行边界

日期：2026-10-20，Asia/Shanghai。依据[用户完整原话](https://github.com/GOD-OF-PPT/chenyuan-wendao/blob/c7190e67a265fe7c8bff63a1db222a434d7dcffd/goal-3/amendments/2026-10-20-idle-clarity-no-compatibility.md)与随后[进一步明确放置玩法设计的原话](https://github.com/GOD-OF-PPT/chenyuan-wendao/blob/c7190e67a265fe7c8bff63a1db222a434d7dcffd/goal-3/amendments/2026-10-20-idle-gameplay-design.md)。本决定覆盖历史方案的冲突部分；v0.3正文和原始输入保持历史原貌，不表示本决定已全部实现。

后继决定：[全玩法放置与游戏交互准则](0006-idle-gameplay-interaction-rules.md)落实用户“每个小玩法/小行动可放置、逐玩法优化交互”的最新要求，覆盖本文较窄的阶段范围与顺序。下文“不自动购买/炼制/旅行/进入战斗”指不执行**未经玩家安排**的动作；玩家明确选择内容、代价与停止边界后，这些玩法同样须支持放置执行。兼容开发/测试暂停继续生效。

## 当前决定

1. 游戏是放置挂机型。体验以持续积累、低频选择、资源规划和阶段突破组成；不以迅速解锁全部境界作为完成标准。完整后期和失败恢复仍须提供，不能以成长慢掩盖断点。没有新规定几分钟、几小时或几天通关。
2. 界面清晰度优先。主舞台保留场景、人物、当前活动、当前目标及一个突出的主动作；成本、读秒、停止原因就近展示。重复标题、并列强调的大量卡片和同时弹出的提示需收敛。常用入口一屏可达；完整配置、物资和账本经清楚入口打开，返回上下文保留，不以隐藏能力或裁切信息减负。青黛墨绿、玉色操作和旧金细节方向保持。
3. 页面兼容开发与测试当前暂停，包括跨浏览器、移动/响应式、分辨率与字号缩放、环境差异矩阵。仅在固定1440×900桌面与单一Chromium环境做必要的当前玩法/交互验证；规则与原子保存验证仍需执行。兼容任务保留暂停状态，不能因每三任务检查或最终矩阵要求自动恢复，不删除原断言或把未执行标绿。

## 已确认的实现偏差

以下为本次静态读码事实，不是实际玩家用时或数值平衡测试：

- [当前动作时长](../../web/src/action-timing.ts)：自然/辅助吐纳的显示耗时均取CULTIVATE的1.6秒，没有按count增加。
- [当前主舞台](../../web/src/App.vue)：批次可选1、5、20、50及达到目标；达到目标取maxBatch。
- [正式内容表](../../src/full/content.ts)：maxBatch=50，数值版本为full-unbalanced.3。无功法加成、从零修为计算，自然吐纳凡人2次、炼气20次、筑基25次、金丹30次、元婴36次、化神40次即可达本境修为上限。这仅计算修为，不包括材料筹备、战斗、寿元、旅行或突破条件。
- [正式引擎](../../src/full/engine.ts)：在一次指令中循环结算批次，增长仍受实际修为上限/物品/寿元等约束。原子保存正确不能证明放置节奏正确；一次短等待结算长批次是必须处理的设计差距。

旧v0.3与Goal1的“不新增挂机”由本次用户定位覆盖。此前读秒用于动作反馈，不能继续把它当作长期成长节奏的验收依据；加速自动化飞升路线只能说明规则连通。

## 后续实施约束

### 放置玩法的开发方向

以下是后续逐项细化和实施的设计，尚未接入当前试玩程序：

| 环节 | 玩家操作与游戏行为 | 需要保持的约束 |
| --- | --- | --- |
| 安排活动 | 在已有修炼方式或确定的采集/宗门委托中选择一项持续活动，开始后显示当前活动及下一周期倒计时 | 复用现有修炼、材料和货币来源；先只允许一个成长活动，避免多个入口同时隐性扣费；不新增签到、体力或新经营系统 |
| 周期积累 | 每个完成的周期按实际条件与成本结算，当前周期尚未完成时不领取未来收益 | 周期时长和产出表须共同设计；不能把原50次结算换个“挂机”标签；一次周期的成功以原子保存完成为准 |
| 阶段目标 | 选择本境修为或当前短缺材料作为活动目标，达到目标、预算不足、寿元边界或状态不允许时停止并说明原因 | 不自动购买/炼制/旅行/进入战斗；满修为不再空转，不自动跳到下一个境界 |
| 定期决策 | 玩家回来查看持续摘要，决定继续积累、换活动、调整既有功法/法宝或投入灵石加速 | 修炼效率与材料/灵石机会成本有实际取舍；不要求每个周期点确认或反复看强动画；完整成本与账本可回看 |
| 筹备突破 | 用积累的资源选择确定/替代获取路线，制作或购买突破物，核对后主动突破 | 保留实际修为与物品条件；境界提升开启新的积累和搭配目标，后期内容与失败恢复不能断档 |

主舞台对应这一循环，只突出当前活动/下一周期、真实修为与材料目标、一个主要操作（未开始时开始，进行中时暂停，阶段就绪时查看筹备）。功法、资源分配和完整记录通过明确的次要入口打开；全功能入口与返回保留在一屏，不同面板不重复抢占主动作位置。普通周期用克制、持续可读的反馈，突破才使用较强演出。

实施顺序分成可独立验证的小项：先完成主舞台信息与操作层级；再确定并实现修炼的周期/停止/保存合同；随后把已存在的采集/委托接入同一活动机制；最后按各境收益、成本、功法差异与恢复路径调节长期节奏。不得一次展开全部机制或用加速演示代替实际成长评估；每个实施项开始前须记录具体参数、验收及回滚。

先明确周期、计划/停止、消耗、满修为后处理、刷新恢复和并发归属，再逐任务实现放置进度。一次受理不能在短周期内兑现整批长期积累；停止后不得暗中继续消费，已完成周期与未完成周期须有清楚边界。突破由玩家在修为及物品条件满足后主动确认，不随挂机自动连跳境界。具体数值继续标记未平衡，需要实际节奏与资源取舍验证。

“挂机”尚未具体规定离线收益、后台追赶或收益上限；这些边界需在对应机制实施前明确，不能默认无限离线结算、擅自补发资源或冒称已实现。查看/阅读不成为隐性消费来源，持续活动及实际消耗必须可见、可停止；所有成长仍走commandId/runId/expectedRevision和原子持久化。

当前先修订约束；已有未提交的UI和验证工具保留为在途结果，不一并宣称交付。原完整UI/性能矩阵与CI分片扩展停止推进，不触发含兼容项的整套执行；未执行/失败保留。后续每次只完成一个可独立验证任务，区分实现、固定环境检查、成长平衡和真实用户验收。
